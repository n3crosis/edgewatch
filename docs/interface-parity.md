# Investigation interface and remaining parity work

The supplied Nightwatch parity audit was reviewed against the repository. It is based on public documentation and source inspection; it does not establish authenticated visual parity with Nightwatch.

Implemented investigation flows:

- Monitoring: Dashboard and Issues. Activity: Requests, Traces, Exceptions, Queries, and the existing event views. Operate: Pipeline and Setup.
- Requests groups retained request executions by HTTP method and Laravel route **name**, falling back to the captured route **template** for unnamed routes, with count, average, exact nearest-rank p95, and complete status families. Requests with neither field use an explicit unknown bucket. Route names and templates are separate group kinds, so identical strings cannot merge unrelated routes. Migration 0019 adds template storage; historical rows retain unknown templates rather than guessing from concrete URLs. Select a group to inspect executions, filter by HTTP status and minimum duration in milliseconds, and open the trace. The drilldown also shows request volume, 5xx counts, and exact bucket p95 trends using those filters. These occurrence filters do not alter the route-list aggregates. Trace filters and pagination are encoded in URLs.
- Logs displays individual entries newest first, with message search, severity, captured context, and a link to the originating execution. The older grouped API remains supported. `entry=<id>` opens a shareable log inspector with context and origin availability; `/log-entries/:id` resolves the entry within project, environment and time bounds independently of feed search, level and cursor. Missing entries and unavailable originating executions are explicit. Closing the inspector restores focus to its entry link or feed controls.
- The EdgeWatch Laravel client captures `EDGEWATCH_ENVIRONMENT` (default `APP_ENV`, maximum 128 characters) on execution records. Migration 0021 stores the environment on traces. Missing values remain unknown, including historical data and official-agent records without the extension. Trace lists and details display it; the trace filter matches the exact captured value. The dashboard environment selector scopes investigation pages and is preserved in navigation and shared URLs. Choosing All environments includes unknown values. Pipeline and Setup remain project-wide.
- Investigation APIs accept an exact `environment` query parameter for overview, request groups/trends, traces (including raw/detail/related), exceptions, queries, log entries and grouped event/user views. Child records match the captured execution environment through both project ID and trace ID. Missing environments do not match a named environment. `/v1/projects/:id/environments` lists names captured in retained traces (up to 200). Issue lists in an environment show groups with retained unhandled occurrences in that environment and time window; issue detail impact counts are environment-scoped. Issue status, lifecycle history and first/last-seen metadata remain project-wide, explicitly identified by `lifecycle_scope: "project"`; changing status affects all environments. Pipeline, usage, permissions and project settings remain operational/project views.
- Trace details expose storage availability and the reported count of records discarded by storage limits. Missing blobs and capped records show an incomplete-data notice; zero reported discards is not a guarantee of full client capture.
- Trace detail tabs (`tab=timeline|records`), event-type filters (`type`) and selected events (`span`) are URL-backed. API span IDs derive from stored record content so links survive reordering and unrelated record removal. Removed events show an unavailable notice. Event buttons support keyboard activation and focus restoration after closing details. The waterfall includes late child events and safely renders instantaneous traces.
- User details link to Requests, Jobs, Exceptions and Logs with exact captured user IDs (including literal `all`), preserving project/environment/time scope. Those activity views expose a User ID filter and carry it into group detail navigation. Request counts/trends, job summaries/attempts, exception counts/trends/latest stack/occurrences and log entry detail use the same user predicate. Missing user metadata is not inferred from another execution.
- Traces supports exact captured user ID and server name filters, combined with source, status, duration and search. Filter changes reset pagination and remain shareable in the URL.
- Queries and Exceptions search/filter controls and list offsets persist in URLs, including detail links and Back navigation. Their APIs filter grouped results before paging (200 query groups / 100 exception groups); query sorting by total duration, calls or p95 applies to the full matching population. Search uses literal contains matching across displayed SQL/connection/hash or exception class/message/file. Exception groups are handled only when every occurrence in the selected scope was handled. Mixed groups appear in the Unhandled view and carry a mixed badge; detail displays handled/unhandled occurrence counts. Counts and classification respect the same project, environment, user and time scope. Responses include `next_offset`; ties use the group identity for stable ordering.
- Project and time range are represented in URLs. Relative presets (1h/6h/24h/7d) and fixed start/end windows are supported. The Custom picker accepts local times and stores absolute Unix milliseconds in `range=custom:<start_ms>:<end_ms>`. Both bounds are inclusive; invalid or reversed bounds return 400. Lists, aggregates, trends, exception stacks, query samples and event details use the same bounds. Issue lists filter current lifecycle records by last-seen time; historical windows do not reconstruct historical issue status. Investigation links preserve this scope, including when opened in a new tab.
- Issues persist independently of telemetry retention. Unhandled exceptions create groups using the existing class/code/file/line fingerprint (version 1); migration 0018 backfills retained unhandled exceptions. A later occurrence reopens a resolved issue. Ignored issues remain ignored. Status changes require an admin key, a reason, and the current `expected_revision` (with optional `expected_status`); stale updates return 409, including when a status has changed away and back. Each successful lifecycle change increments the revision, including automatic reopening. Mutation and audit writes commit together; competing updates cannot leave phantom history. History records the operator key name, reason, status and timestamp. Impact counts describe retained data, not lifetime totals. The exception-detail link follows the selected time window.
- Read keys cannot change settings, replay messages, or update issues. Admin keys can read and mutate. Issue lifecycle data requires a connected API; the seed dashboard does not simulate issue state.
